## Story

**As a** ISKR,
**I want** medir o preview e ajustar até bater todas as metas,
**so that** o objetivo do projeto — sair de 56 para 90+ — esteja comprovado antes do go-live.

## Acceptance Criteria

1. PageSpeed/Lighthouse **mobile** no preview: Desempenho ≥ 90, FCP < 1,5s, LCP < 1,5s, TBT < 100 ms, CLS < 0,1.
2. Lighthouse **desktop** registrado, sem regressão em relação ao mobile.
3. Acessibilidade ≥ 87, com os contrastes da `docs/front-end-spec-mobile.md` §6 verificados.
4. Relatórios de antes e depois guardados em `docs/reference/lighthouse/`, com data no nome.
5. Sem rolagem horizontal em 360, 390, 768, 1280 e 1920 px, com evidência por breakpoint.
6. Orçamento de performance respeitado (`docs/architecture.md` §7.1): 0 KB de JS, CSS ≤ 15 KB comprimido, HTML ≤ 60 KB comprimido, fontes ≤ 4 arquivos e 120 KB somados, imagem do LCP ≤ 150 KB.
7. Toda imagem com `width`/`height` explícitos; só a do hero com `fetchpriority="high"`.
8. Se alguma meta não for atingida, a causa e o ajuste feito ficam registrados nas notas de conclusão.

## Dev Notes

⚠️ **Dependência bloqueante:** todas as medições exigem a URL de preview da Vercel, que depende da Story 1.1 AC10 (@devops, com credenciais do Lucas). Enquanto o preview não existir, é possível medir localmente com `npm run build && npm run preview` e Lighthouse local — mas o AC só é dado como cumprido com medição no preview real.

**Baseline do site atual, para comparação** (auditado em 17/09):

| Métrica                 | Antes                         |
| ----------------------- | ----------------------------- |
| Desempenho mobile       | 56                            |
| FCP / LCP / Speed Index | ~10s cada                     |
| JS transferido          | ~3,4 MB                       |
| Fontes                  | 12 arquivos `.woff`, > 1,5 MB |
| TBT / CLS               | 10 ms / 0                     |
| Acessibilidade          | 87                            |

**A causa da nota 56 era render no cliente**, não execução pesada (TBT já era 10 ms) nem layout instável (CLS já era 0). Se o rebuild ficar abaixo de 90, o problema provavelmente está em **peso de fonte, peso de imagem ou CSS grande demais** — não em JS, que deve ser zero.

**Ordem de investigação recomendada quando faltar performance:**

1. Tamanho e formato da imagem do LCP.
2. Número de fontes com `preload` (deve ser exatamente uma).
3. Tamanho do CSS inlinado (se passar de 15 KB, `inlineStylesheets: 'auto'`).
4. Requisições no caminho crítico (meta: até 6).

**Perfil de medição:** Moto G em 4G, que é o padrão do PageSpeed mobile.

**Não vale otimizar quebrando fidelidade visual sem avisar.** A regra aprovada permite mudança visual por performance, mas ela precisa ser **registrada** na story para o Lucas ver na Story 2.2.
